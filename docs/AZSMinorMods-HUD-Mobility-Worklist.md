# Slim Suite HUD mobility worklist

## Editing controls and action slots

The movable Done panel offers a dropdown for isolating one element's editing handles/previews and an `ALL?` button to restore every editor handle. These choices are mutually exclusive and do not change saved feature visibility. The normal live HUD remains visible for positioning context. The cast-bar mover has been removed.

Fresh installs leave the game's action bar and other native UI in place. Opening **Toggle UI Settings** alone only opens the editor; each replacement stays off until its own setting is enabled. The custom racial slot is off by default; **Add racial ability as a 7th Action Bar 1 button?** opts in to ActionButton12. When enabled, it sits after the six spell slots with a distinct gold border. Horizontal and vertical layouts use compact square slots, and action-bar width/height controls resize the slots proportionately instead of creating blank container space. All mover outlines now follow the same visible bounds as screen-edge clamping.

Right-click width, height, scale and supported padding values accept the mouse wheel over their labels or +/- controls. They invoke the same adjustments as clicking. Attach/detach build rows is offered only on Build spell row. Local Lua checks cover seven-slot placement in both orientations, ALL/single-element/locked transitions, and wheel/click adjustment equivalence. Native visuals and interaction still require an in-game check.

## Screen-edge movement and scale

Movement, clamping, snapping comparisons and saved absolute positions now use UIParent coordinates. Native frame coordinates and SetPoint offsets use each frame's effective scale, so convert explicitly in both directions. Never subtract bounds from differently scaled frames without conversion. Legacy saved positions are migrated once and tagged `coordinateSpace = "uiParent"`.

The XP bar uses its current oriented width and height rather than stale horizontal child extents. Action/party groups and buffs use their visible controls; buffs no longer reserve the empty parent container. A local Lua check compiled the addon and exercised 48 XP edge cases across six scales and both orientations, plus differently scaled buff bounds. These checks use mocked native frames, not a running game; native artwork and actual dragging still require an in-game check.

This tracks the requested movable HUD elements and the limits established by the current supplied addon API documentation (`addon_docs(2).md`). The action bar, build rows and announcement banner are separate game elements; do not combine them just because the game originally groups or positions them together.

## Stored-levels “Level Up!” button

**Status: implemented locally; not verified in-game.** Slim Suite now offers a movable replacement button, controlled by the `Replace Default Level Up with Movable Version?` setting. It uses `AZS_OpenStoredLevels()` to open the game's native choices and hides/restores the original through `AZS_SetHudShown("levels", ...)`. The button is a separate `MOVABLE` entry, so the existing Unlock UI handle provides move, resize, scale and optional snap behavior. It is hidden until `AZS_GetStoredLevels()` reports at least one unspent level, and its counter shows the full number waiting to be spent. The count is polled every 0.25 seconds so the button appears again as soon as a new point becomes available and disappears once all points are spent. Its hover effect grows 6% around its existing visual center and restores its saved anchor when the pointer leaves, so it should not slide away from its resting spot. It also uses the matching class symbol from the game's character-creation class-icon atlas (for example, Priest characters show the Priest icon); the native stored-level API does not provide the icon directly, so the replacement resolves it from the player's class. The native choice screen remains game-owned and unchanged. On clean logout or `/reload`, Slim Suite now restores every native HUD visibility value it changed before the game saves settings; this lets the game's own controls return if Slim Suite is disabled for the next session.

Local package: `dist/AZSMinorMods-LevelUp-Movable-LocalTest.zip`.

## Six-spell / four-item build rows

**Status: implemented locally; not verified in-game.** The optional replacement has separate movable six-spell and four-item rows. By default, the spell row is above the jewelry row and both occupy the lower-left-center area shown in the native-layout reference; the jewelry row attaches directly beneath the spell row. The spell row follows `AZS_SPELLS` order (the racial entry is last), first matching ready loadout icons by the documented stable ability key or exact spell IDs, then resolving the canonical spell ID against the 1.12 spellbook. Hover uses the native spellbook tooltip when the spell maps to a spellbook entry; the supplied API otherwise provides only key, spell ID, rank and cooldown, so no description is invented. The item row reads only neck, finger and trinket equipment slots (API slots 2, 11–14), retaining first-observed equip order; four of the five possible jewelry items display at once. Inventory-change events and a light polling fallback refresh the rows. A bundled catalog supplies display names when an inventory link is unavailable; native item tooltips come from the game.

The item row records each item's first observed equipped order in SavedVariables, so reloading or moving the same jewelry item between slots retains its place. On a fresh profile, already-worn items are ordered by the first slot scan (neck, fingers, then trinkets); the game/API does not expose when the player originally acquired those items. When enabled, the rows start attached with a small gap and spells above jewelry, at the lower-left-center position shown in the default-UI reference. **Reset UI** restores that same position and attachment. Detaching preserves both current positions; reattaching keeps the spell row where it is and places the jewelry row below it. Either row can be moved, resized, scaled, snapped and oriented independently. A setting replaces the native combined spell/jewelry rows through the documented `AZS_SetHudShown("build", shown)` API and can restore the user's prior visibility state. Each custom row can be hidden through its own movable-feature controls.

The provided Aethus API documentation exposes `AZS_SetHudShown("build", shown)` for the native spell and jewelry build rows together, plus `AZS_SPELLS` for spell data. It does not document separate native visibility controls or an item-acquisition history. In-game checks are still needed for the game's spellbook ID/icon mapping and inventory texture/link APIs.

## Encounter bar targeting and tooltip size

Encounter rows now accept clicks and call the game's exact-name target command for the displayed boss, guardian or elite. They do not use a nearest-enemy fallback. The row tooltip shows the unit role and current health. Encounter health reads the API's current/max values on `AZSUNITS` updates, without a second polling loop. The shared game tooltip has a 260×140 preferred default; its wrapping width is applied before the native tooltip lays out its rows, and its frame height expands to the measured content height to keep the final row inside. The UI settings page and in-world right-click controls can resize it. Code path reviewed; actual tooltip layouts and encounter update timing still need in-game verification.

## Buff layout direction

The Buffs resize menu now offers horizontal/vertical layout, a separate Grow up/Grow down control, and adjustable icon spacing. Horizontal buffs wrap into additional rows in the selected direction; vertical buffs extend as a column in that direction. In vertical mode, resizing the frame height controls how many icons fit before the next column. This is implemented locally and still needs in-game verification.

## Event announcement banner (for example, “Hogger enters the battlefield!”)

**Status: implemented locally; not verified in-game.** The custom banner uses the API's localized `banner.text` and event metadata, rather than treating chat text as the sole source. It lasts 10 seconds total, fading in for 0.6 seconds and out for 0.6 seconds. Its own Unlock UI handle moves, resizes and scales it; boss events use the red style flag. It remains a separate element from “Move to Begin.”

The game API also exposes the same events to chat in some cases; chat is useful for comparison but isn't needed to reconstruct the announcement text. The addon's event-handler path receives the localized string directly, even while native banners are hidden. The frame clamps to the current screen after placement or resize while leaving larger saved coordinates intact for later display changes.

## Run clock, next-boss line, and active encounter bars

**Visibility fix, clock orientation, and layout padding implemented locally; not verified in-game.** The run clock and next-boss line stay paired in one movable element, centered independently from encounter bars. Its right-click menu switches between a compact vertical stack (the default) and a horizontal line. Custom encounter bars remain separate and are now driven by run phase and `AZS_UNITS`, whether or not the player had the original boss HUD enabled; the earlier native-visibility gate could make the replacement disappear. Their default anchor starts in the upper-left encounter area beside the player frame, matching the reference HUD's separation between the left-side active target frame and centered run clock. Fresh horizontal layouts use 252×72-pixel cards with larger 13-pixel names and 12-pixel health bars to approach the reference frame's relative size; horizontal cards grow from that anchor, while vertical bars remain narrow and distribute across however many live targets are present. Existing saved sizes and positions are preserved. Padding controls are available for the addon's custom clock, encounter, tally, announcement, and buff layouts; native frames whose internal content layout is game-owned keep their native padding. Saved absolute positions are clamped to the current screen without overwriting the saved larger-display coordinates. Encounter bars are re-clamped after their live width or height changes as targets come and go. The native clock and boss/guardian bars are restored when their replacements are not active. The documented encounter list provides name and health but no per-unit portrait key; do not fabricate portraits for the custom cards.

Local package: `dist/AZSMinorMods-UI-controls-local-2026-11-01.zip`.

## Tooltip

The tooltip is in the movable list with a 260×140 preferred size. Width is set before the native layout pass; content that wraps to more rows grows the tooltip vertically so text stays within its bounds. The UI settings page offers smaller/larger controls, and the in-world right-click controls allow width, height and scale changes. It remains game-owned and keeps its own content. This layout fix has not yet been verified against the live client's range of tooltip contents.

## Movable damage meter and layout controls

Slim Suite's movable meter now reads the creator's version-1 `AZS_GetMeterContext` / `AZS_GetMeterSnapshot` contract from `addon_docs(2).md`. It offers My Damage, performed My Healing, Boss Damage, and Group Damage, with amount/rate sorting, a scrollable full source list, and group-member ability drilldown. Damage and healing resets use independent session-only checkpoints, release replaced tokens, and recover when a token expires or the run/authority/epoch changes. Boss Damage follows native encounter boundaries, and Group Damage offers no reset. Totals and average rates always come from the authoritative snapshots; rows and contributions are never added together. The meter now reports documented `absorb_consumed` contributions separately from healing and shows the current aggregate shield when available. The API only identifies Soul Link consumed absorbs as an absorb contribution; it does not expose a historical per-spell absorb breakdown for shields such as Power Word: Shield or Ice Barrier. Rows show observed Min Hit, Max Hit, Min Crit, Max Crit and Crit %; the combat-text stream does not contain earlier hits, so those values are session observations and may say Not recorded. Text is fit to the available row width, and the meter's movable handle provides resize/scale controls. On a fresh profile, its replacement starts at the bottom-right edge with a small inset, matching the user's reference screenshot. It hides and restores the native meter through `AZS_SetHudShown("meter", ...)`, rather than trying to move an undocumented native frame. Its Unlock UI handle provides move, resize, scale and global snap behavior. The draggable Done/control panel now contains grid visibility, 32/64/128/256 divisions, vertical and horizontal red center-line toggles, and global snapping; the main Slim Suite settings window closes when UI editing starts. These changes are local and still need in-game verification.

## 0.138.0 world-anchored combat text API review

Slim Suite currently does not draw floating combat-number text, so the new `AZS_GetCombatTextEvents()`, `AZS_ProjectCombatTextAnchors()` and `AZS_RegisterCombatTextFrameHandler()` APIs do not change an existing Slim Suite feature. They could support a future custom damage-number display that stays attached to the enemy or death location through camera movement, including targets without nameplates. The movable event-announcement banner is a different feature and remains unchanged.

## 0.139.0 API and behavior cross-check

The creator's exact 0.139.0 patch note is at the top of `assets/changelog.txt`, which supplies the launcher's home News panel. The note says combat-text events now include `meterSource` and `meterSourceKey`. The Slim Suite meter uses `meterSourceKey` to associate sampled hits with the meter's canonical source and uses snapshot `share` for each row's percent of total damage. The supplied `addon_docs(2).md` predates 0.139 and does not document those two event fields, so their runtime shape still needs confirmation against the updated client. The engine update itself does not change the guide's unrelated class or gameplay facts.

The provided docs expose live bosses in spawn order through `AZS_GetBosses()` and awake state through `AZS_GetGuardians()`. Slim Suite now assigns Skull, X, Circle and Star in that order, with awake Guardians following the real-boss list; it refreshes on unit updates and rechecks every 0.75 seconds. On a changed order it attempts to remove its previous marker before assigning the new one, and duplicate-name spawns are only cleared/marked when their API ID can be confirmed on the current target. This is a code-level correction; raid-target behavior still needs an in-game check. The separate old name-based miniboss table/control is no longer presented as authoritative.

For the minimap, the docs expose Guardian lair `mx/my` coordinates and the existing `AZS_SetHudShown("flag", …)` toggle for the game's nearest-lair flag. They do not provide boss positions or a documented projection of all live boss/Guardian positions onto the minimap. The current setting only toggles the game's nearest Guardian lair flag; it does not draw custom pins for every boss or lair. Full custom markers require an API with those positions/projection rules.

For buff detail, the API gives the current aggregate shield (`AZS_RUN.sh`), aggregate damage-reduction stat (`AZS_STATS.arm`), and buff spell IDs with remaining time (`AZS_BUFFS`). It does not map a particular buff to its absorb amount or damage-reduction percentage, nor document the numeric unit for `arm`. Slim Suite must not attach those totals to an individual buff or invent a percentage conversion. Per-buff details need a richer creator API; an aggregate display also needs the creator to document `arm`'s unit before it can safely show a percent.

The encounter replacement uses the API's `hp/hpm` values and update messages rather than repeatedly sampling each frame; there is no finer documented health-update event in the supplied docs. The change favors current API accuracy while keeping polling limited. This remains subject to an in-game check for the API's actual update cadence.

## Screen-edge placement and hiding a feature

Movable frames now clamp the visible child bounds rather than only the parent rectangle. This lets the action bar sit flush to the screen even when its empty parent has an inset around the actual buttons, and its scale is included in the edge calculation. Absolute saved positions use the same bounds. While UI settings are unlocked, Shift+left-clicking a handle or using **Hide feature** in its right-click menu makes the feature transparent and disables its mouse input where the frame API supports restoring it safely. Its handle remains gray and reachable so **Show feature** can restore it. The hidden choice persists across `/reload`. Implemented locally; edge behavior and mouse restoration still need in-game verification across the listed frame types.

## Settings categories and chat filters

Slim Suite opens on **New/Unique, But Minor Features**. At the top of **Chat mods**, the section explains: “The goal of cleaning up chat is to make your friends' chat easier to see in multiplayer.” Independent options hide level-up stat lines, new-spell lines, racial-ability/buff mentions, the specific Oogax Q Warsong Gulch opening line, “Who dares to enter my lair,” and game-authored NPC/boss dialogue and run-roleplay lines. The racial filter matches generic racial wording and the localized name of the racial spell when the game exposes it through the spellbook; it is not a general semantic detector for every possible racial-buff sentence. Player chat is never suppressed. The other settings remain on **Modifying the User Interface**.

The target-frame visibility control and movable level-up replacement are on the UI page. Replaceable custom UI features are worded as questions (“Replace Default … with Movable Version?”); the controls cover build rows, damage meter, run clock, encounter bars, kills/gold/cache, announcements and the level-up button. The plain action-bar-art option is also phrased as a replacement question. Turning off a custom announcement replacement hides its custom banner and restores the native banner display.

The stat-bonus chat filter targets only the stat-gain line; level-up notices and spell-learning lines are controlled independently. Player say, yell, party, raid, guild, officer, channel, emote, battleground and Battle.net chat bypass the filters. The roleplay setting filters game-authored monster say/yell/emote and boss emote/whisper event types, alongside API-published boss/guardian banner text. These behaviors are implemented locally and still need an in-game check.


## Ability tooltip samples

The snapshot API does not expose historical individual-hit extrema or critical counts. Damage hit samples use this addon's independent `AZS_GetCombatTextEvents` cursor; missing batches are reported. Healing and other party members' spell samples use only localized combat-log format strings actually present in the client, on combat-log events. Actor names must map unambiguously to snapshot actor/owner descriptors. Own outgoing damage logs are ignored while the native stream is available to prevent double counting. These samples cannot recover hits before loading or unavailable combat-log events, and the tooltip says Not recorded when no sample exists. Boss tooltip hit samples explicitly include all targets; the boss totals remain encounter-only. A reset clears only that view's samples. Tokens and cursors are never saved across reloads.

Local checks passed for all four queries, amount/rate sorting, an 80-source list, independent reset tokens, boss encounter scope, group drilldown without resets, self/group damage and localized healing tooltips, checkpoint expiry, and new-run cleanup. Native UI and actual game combat-log emission still need an in-game check.
